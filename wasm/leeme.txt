1. DESCRIPCIÓN Y CARACTERÍSTICAS DE LA APLICACIÓN
--------------------------------------------------------------------

La aplicación "WASM vs JavaScript" es un entorno interactivo de análisis
comparativo de rendimiento entre código WebAssembly escrito directamente
a mano en formato texto (WAT) y su implementación equivalente en JavaScript
puro contemporáneo.

La herramienta evalúa la velocidad, consistencia y eficiencia computacional
de ambos entornos sometiéndolos a tres algoritmos matemáticos intensivos:

  1. Factorial de un entero de 64 bits (n!):
     - Calcula el producto acumulativo desde n hasta 1 para valores
       de n entre 1 y 20.
     - Evalúa el procesamiento aritmético con enteros grandes de 64 bits
       (tipo nativo `i64` en WASM frente a `BigInt` y `Number` en JavaScript).
     - Ejemplo: 15! = 1.307.674.368.000.

  2. Coseno por Serie de Taylor (15 iteraciones, precisión completa IEEE-754):
     - Aproxima el coseno trigonométrico de un ángulo en radianes mediante
       el desarrollo en serie de Taylor:
         cos(x) = 1 - x^2/2! + x^4/4! - x^6/6! + ... + (-1)^k * x^(2k)/(2k)!
     - Con 15 términos, el error residual es inferior a 10^-16 (límite físico
       de la precisión de doble precisión de 64 bits `f64`), coincidiendo
       con Math.cos(x) en todos sus dígitos significativos sin ciclos redundantes.
     - Evalúa el rendimiento de operaciones continuas en coma flotante de
       doble precisión (tipo `f64` en WASM frente a números float de JS).
     - No utiliza funciones matemáticas nativas de la librería estándar
       (como Math.cos), midiendo el coste de cómputo aritmético puro en bucle.

  3. Test de primalidad para enteros de 32 bits:
     - Determina si un número dado es primo mediante el algoritmo de prueba
       de divisores impares hasta su raíz cuadrada (d * d <= n).
     - Evalúa el rendimiento ante ramificaciones condicionales intensivas
       y operaciones de resto/módulo (`i32.rem_u` en WASM frente al
       operador `%` en JS).
     - Ejemplo: comprobación del primo 982.451.653 (31.344 comprobaciones de división
       por repetición, evaluado en 2.000 repeticiones para superar el umbral de ruido del temporizador).

Metodología rigurosa de medición (Benchmarking):
  - Calentamiento previo (Warmup) y Tier-up: se ejecutan 10.000 iteraciones iniciales
    para permitir que el motor del navegador (V8, SpiderMonkey, JavaScriptCore)
    compile el módulo WebAssembly al tier óptimo de código máquina nativo (TurboFan)
    y estabilice las optimizaciones JIT.
  - Carga intensiva: cada prueba ejecuta entre 2.000 y 100.000 repeticiones consecutivas
    para magnificar las diferencias temporales y obtener cifras estadísticamente
    significativas que superen con holgura el ruido de los temporizadores de los navegadores.
  - Reducción del sobrecoste de frontera (Boundary Crossing) y benchmarking inlined:
    Además de las funciones individuales, el archivo WAT incluye funciones de benchmark
    internas ($bench_factorial, $bench_coseno, $bench_es_primo) con el cómputo algorítmico
    integrado de forma inlined dentro del bucle. Esto elimina por completo el sobrecoste
    de interoperabilidad JS-WASM en cada llamada y evita la sobrecarga artificial de
    creación de marcos de pila (instrucción call) que wat2wasm no inlínea automáticamente,
    compitiendo en estricta igualdad de condiciones con el inlining que realiza el compilador
    JIT de JavaScript.
  - Temporización de alta precisión: medición mediante la API estándar
    `performance.now()`, con resolución de microsegundos, y cálculo automático
    del factor de aceleración (Speedup = Tiempo_JS / Tiempo_WASM).

2. ARQUITECTURA Y ARCHIVOS DEL PROYECTO
--------------------------------------------------------------------

  · ejemplo.wat   → Código fuente WebAssembly en formato texto (WAT).
                    Escrito manualmente con instrucciones de la máquina de pila
                    de WebAssembly (declaración de tipos, locales, bucles con
                    block/loop/br_if, aritmética i32/i64/f64 y funciones de benchmark
                    con lógica algorítmica inlined).

  · ejemplo.wasm  → Módulo binario compilado a partir de ejemplo.wat mediante
                    la herramienta oficial WABT (WebAssembly Binary Toolkit).
                    Tamaño ultracompacto: únicamente 659 bytes.

  · ejemplo.js    → Controlador y benchmark en JavaScript:
                    - Carga e instanciación asíncrona del binario WASM mediante
                      WebAssembly.instantiateStreaming() con respaldo en
                      WebAssembly.instantiate().
                    - Implementación paralela de los tres algoritmos en JS.
                    - Medición precisa de tiempos de ejecución y cómputo de speedup.
                    - Gestión interactiva de pestañas, formularios y visualización
                      del código WAT con resaltado de sintaxis.

  · ejemplo.html  → Interfaz de usuario construida conforme a las directrices de
                    diseño semántico de HTML5 (sin contenedores div, utilizando
                    header, main, section, menu, form, table, etc.) y accesible
                    (atributos role="tablist", aria-selected, aria-controls, etc.).

  · ejemplo.css   → Hoja de estilos con estética dark moderna inspirada en
                    estándares actuales, tipografías del sistema y legibilidad
                    avanzada para código y métricas tabulares.

  · build.js      → Script de automatización en Node.js que compila ejemplo.wat
                    a binario ejemplo.wasm usando la librería npm "wabt".

  · leeme.txt     → Este documento técnico de especificación.

3. CARACTERÍSTICAS TÉCNICAS DEL CÓDIGO WAT IMPLEMENTADO
--------------------------------------------------------------------

El módulo `ejemplo.wat` se diseñó respetando el estándar oficial de W3C
WebAssembly Core Specification:

  - Máquina de pila (Stack-based Virtual Machine):
    Las operaciones consumen y depositan valores en la pila de evaluación.
  - Sistema de tipos estático y explícito:
    Uso de `i32` (enteros 32 bits), `i64` (enteros 64 bits) y `f64` (reales
    IEEE-754 de doble precisión).
  - Estructuras de control estructuradas:
    Uso de bloques `block` y `loop` combinados con instrucciones de salto
    condicional `br_if` y saltos incondicionales `br` a etiquetas semánticas,
    garantizando un flujo estructurado sin punteros de instrucción arbitrarios.
  - Instrucciones aritméticas nativas:
    `i64.mul`, `i64.sub`, `i64.le_u` para enteros grandes; `f64.mul`, `f64.div`,
    `f64.add`, `f64.neg` para el cálculo del coseno; e `i32.rem_u`, `i32.mul`,
    `i32.eqz` para el análisis de divisibilidad en números primos.
  - Exportación de interfaz pública:
    Exportación de 6 funciones: 3 de cálculo directo (`factorial`, `coseno`,
    `es_primo`) y 3 de bucle interno de benchmarking (`bench_factorial`,
    `bench_coseno`, `bench_es_primo`).

4. VENTAJAS DE WEBASSEMBLY FRENTE A JAVASCRIPT
--------------------------------------------------------------------

4.1 Rendimiento predecible y casi nativo (Predictable Near-Native Speed):
    - JavaScript es un lenguaje dinámico interpretado que depende de motores
      JIT (Just-In-Time) complejos (como V8 en Chromium, SpiderMonkey en Firefox
      o JavaScriptCore en Safari). Si los tipos de las variables varían o el motor
      heurístico falla en sus asunciones, se produce una desoptimización ("deopt
      bailout"), degradando severamente el rendimiento a mitad de ejecución.
    - WebAssembly, por el contrario, posee un formato binario ya tipado y
      validado que se traduce de forma directa y predecible a código máquina del
      procesador anfitrión (x86_64, ARM64) en una única pasada rápida. No sufre
      desoptimizaciones inesperadas, lo que garantiza tiempos de ejecución
      estables y deterministas, ideales para cómputo en tiempo real o simulaciones.

4.2 Tipos nativos de 64 bits (Soporte directo de enteros `i64`):
    - Tradicionalmente, JavaScript solo ofrecía el tipo `Number` (formato
      IEEE-754 de 64 bits de coma flotante), cuya precisión entera exacta está
      limitada a 53 bits (Number.MAX_SAFE_INTEGER = 9.007.199.254.740.991).
      Cualquier factorial o cálculo superior a 20! desbordaba o perdía precisión.
      La introducción de `BigInt` en JS resolvió la precisión, pero penaliza
      fuertemente el rendimiento al ser un objeto asignado en memoria dinámica
      (heap) con sobrecoste de recolección de basura.
    - En WebAssembly, `i64` es un tipo primitivo nativo de CPU: una operación
      `i64.mul` o `i64.sub` se mapea directamente a una única instrucción
      ensambladora del microprocesador (como MUL/SUB en x86-64), ejecutándose
      en un único ciclo de reloj.

4.3 Ausencia de sobrecoste por Recolección de Basura (Garbage Collection):
    - La ejecución de JavaScript genera objetos y contextos en memoria que deben
      ser periódicamente rastreados y liberados por el Garbage Collector (GC),
      provocando pausas intermitentes ("GC pauses" o "jank").
    - Los algoritmos numéricos en WebAssembly operan íntegramente sobre la pila
      de ejecución o sobre un búfer de memoria lineal contigua (ArrayBuffer), sin
      intervenir en el ciclo de vida del recolector de basura de JavaScript.

4.4 Tamaño binario ultracompacto y descompresión instantánea:
    - El binario `ejemplo.wasm` pesa escasos 459 bytes. Un módulo equivalente en
      JavaScript requeriría un tamaño sustancialmente mayor en bytes de texto.
    - El análisis sintáctico (parsing) de texto JavaScript consume tiempo de CPU
      al cargar la página. El formato binario de WASM está diseñado para ser
      decodificado y validado en paralelo a la velocidad de la red a medida que
      se reciben los bytes (streaming compilation).

4.5 Seguridad por diseño (Memory-Safe Sandbox):
    - WebAssembly se ejecuta dentro del mismo entorno aislado (sandbox de seguridad)
      que JavaScript en el navegador, sujeto a la política de mismo origen
      (Same-Origin Policy).
    - No permite saltos a direcciones de memoria arbitrarias ni ejecución de código
      fuera de su espacio de direcciones lineales acotado, previniendo vulnerabilidades
      clásicas de lenguajes nativos como buffer overflows que comprometan el sistema.

4.6 Complementariedad e interoperabilidad con JavaScript:
    - WebAssembly no pretende reemplazar a JavaScript, sino complementarlo.
      JavaScript continúa siendo el lenguaje idóneo para manipular el DOM,
      responder a eventos de interfaz y gestionar APIs web de alto nivel, mientras
      que WebAssembly actúa como motor de cálculo para tareas intensivas en CPU
      (criptografía, procesamiento de audio/vídeo, motores físicos, compresión, etc.).

5. INSTRUCCIONES DE EJECUCIÓN Y COMPILACIÓN
--------------------------------------------------------------------

5.1 Ejecución en navegador local:
    Debido a las políticas de seguridad CORS de los navegadores modernos, los
    módulos WebAssembly no pueden cargarse mediante el protocolo `file://`. Se
    requiere un servidor HTTP local.

    Opción 1 — Servidor Python (disponible de forma nativa en macOS):
      cd /Users/raul/Desktop/Standards-and-Web-Computing/wasm
      python3 -m http.server 8000
      Abrir en el navegador: http://localhost:8000/ejemplo.html

    Opción 2 — Servidor Node.js:
      npx serve .
      Abrir en el navegador la dirección indicada en la terminal.

5.2 Recompilación de WAT a WASM (opcional):
    El repositorio ya incluye el archivo binario `ejemplo.wasm` precompilado.
    Si se realizan modificaciones sobre `ejemplo.wat`, se puede recompilar con:
      npm install
      node build.js
    El script `build.js` lee `ejemplo.wat`, invoca la librería oficial `wabt` y
    escribe el archivo resultante `ejemplo.wasm`.
